# csv-tidy 要件定義書

- 版: 0.1（初版）
- 作成日: 2026-09-24
- 対象リリース: v0.1（MVP）。v0.2 以降は概要のみ記載

## 1. 目的と背景

CSV データを使いやすい形に整える Web アプリケーションを開発する。
主な目的は学習とポートフォリオであり、要件定義→設計→実装→テストという開発の過程をリポジトリに記録する。
このため、機能を広げることよりも、各段階の品質（テスト・ドキュメント・設計の説明しやすさ）を優先する。

## 2. 決定事項サマリ

| 項目 | 決定内容 |
| --- | --- |
| 提供形態 | Web アプリ（ブラウザから操作） |
| 主な利用者 | 開発者本人（学習・ポートフォリオ目的） |
| 実装言語 | Python |
| 構成 | FastAPI（API）＋軽量フロントエンド（HTML/JS）。整形ロジックは Web に依存しない純 Python のコアとして分離する |
| 実行環境 | ローカル実行のみ（クラウド公開はしない） |
| 操作フロー | アップロード → プレビュー → 処理選択・適用 → 変更前後の比較 → ダウンロード |
| 進め方 | MVP（v0.1）から機能を段階的に追加する |

## 3. スコープ

### 3.1 リリース計画

| 版 | 機能分類 | 内容 |
| --- | --- | --- |
| v0.1 | 文字コード・改行の正規化 | 入力文字コードの判定、出力文字コードと改行コードの選択 |
| v0.1 | 空白・空行・重複の除去 | セル前後の空白トリム、空行の削除、重複行の削除 |
| v0.2 | 列の操作 | 列の選択・並べ替え・リネーム・削除、ヘッダー名の正規化（詳細は未定） |
| v0.3 | 値の正規化 | 全角英数→半角、日付形式の統一、数値の桁区切りカンマの除去など（詳細は未定） |

### 3.2 v0.1 のスコープ外

- 区切り文字の選択・自動判定（TSV など）
- ヘッダー行の有無の切り替え（1行目は常にヘッダーとして扱う）
- キー列を指定した重複判定
- 変更内容のサマリレポート（例:「重複を N 行削除」）
- 処理設定の保存と再利用
- 10MB を超えるファイル、ストリーミング処理
- 認証、複数ユーザー対応、クラウドへのデプロイ

## 4. 機能要件（v0.1）

### 4.1 ファイル入力

| ID | 要件 |
| --- | --- |
| FR-01 | ブラウザから CSV ファイルを1つアップロードできる |
| FR-02 | ファイルサイズの上限は 10MB とする。超えた場合は処理せずエラーを表示する |
| FR-03 | 区切り文字はカンマに固定し、RFC 4180 に準拠して解析する（ダブルクォートで囲まれたセル内のカンマ・改行・エスケープされた `""` を正しく扱う） |
| FR-04 | 1行目は常にヘッダー行として扱う |

### 4.2 文字コード・改行の正規化

| ID | 要件 |
| --- | --- |
| FR-10 | 入力の文字コードは UTF-8（BOM 付き・BOM なし）と CP932（Shift_JIS の Windows 拡張）の2種類を対象とする |
| FR-11 | 文字コードは UTF-8（BOM 付き）→ UTF-8 → CP932 の順に試して自動判定し、判定結果を画面に表示する |
| FR-12 | 利用者は判定結果を手動で上書きし、再読み込みできる |
| FR-13 | どの文字コードでもデコードできない場合はエラーを表示し、処理を中止する |
| FR-14 | 出力の文字コードは UTF-8 / UTF-8（BOM 付き、Excel 向け）/ CP932 から選べる。既定値は UTF-8 |
| FR-15 | 出力の改行コードは LF / CRLF から選べる。既定値は LF |
| FR-16 | CP932 で表せない文字があるときは、勝手に置換せずエラーとし、該当箇所（行・列）を表示する |

### 4.3 空白・空行・重複の除去

各処理は個別にオン・オフできる。

| ID | 要件 |
| --- | --- |
| FR-20 | 空白トリム: 各セルの前後にある半角スペース、タブ、全角スペース（U+3000）を除去する。セル内部の空白は変更しない |
| FR-21 | 空行の削除: すべてのセルが空（トリムを有効にしている場合はトリム後の値で判定）の行を削除する。まったく何もない行もこれに含む |
| FR-22 | 重複行の削除: 全列の値が一致する行を重複とし、最初に現れた行を残して以降を削除する。値の比較はトリムなどの処理を適用した後の値で行う |
| FR-23 | ヘッダー行は空行の削除と重複行の削除の対象外とする（トリムは適用する） |
| FR-24 | 処理は「デコード → 解析 → 空白トリム → 空行の削除 → 重複行の削除 → エンコード」の順に適用する |

### 4.4 不正な行の扱い

| ID | 要件 |
| --- | --- |
| FR-30 | ヘッダーと列数が異なる行があっても処理は中止しない |
| FR-31 | そのような行は内容を変えずにそのまま出力し、画面に警告として元ファイルでの行番号と列数を表示する |

### 4.5 プレビューと出力

| ID | 要件 |
| --- | --- |
| FR-40 | アップロード後、先頭の数行（初期値 50 行・仮定）を表形式でプレビューする |
| FR-41 | 処理を適用した後、変更前と変更後のプレビューを比較できるように表示する |
| FR-42 | 整形後の CSV をダウンロードできる。ファイル名は元の名前に `_tidy` を付けたもの（例: `data.csv` → `data_tidy.csv`・仮定） |

## 5. 非機能要件

| ID | 分類 | 要件 |
| --- | --- | --- |
| NFR-01 | 性能 | 10MB の CSV の処理が一般的なノート PC で数秒以内に終わる（目安） |
| NFR-02 | セキュリティ | サーバーは `127.0.0.1` のみで待ち受ける。アップロードされたデータはメモリ上だけで扱い、ディスクやログに内容を残さない |
| NFR-03 | 保守性 | 整形ロジック（コア）は FastAPI に依存させず、単体でテストできるようにする |
| NFR-04 | テスト | コアはユニットテスト（pytest）、API は結合テストで検証する。境界条件（BOM、全角スペース、クォート内の改行、空ファイル、ヘッダーのみのファイル、不正な行）をテストケースに含める |
| NFR-05 | 再現性 | README の手順だけでセットアップと起動ができる |
| NFR-06 | 実行環境 | Python 3.12 以上（仮定） |

## 6. 受け入れ基準（v0.1）

1. CP932 で保存された CSV をアップロードすると文字コードが CP932 と判定され、UTF-8（BOM 付き）+ CRLF で出力したファイルを Excel で開いても文字化けしない。
2. `"  山田　"`（前後に半角と全角の空白）のセルが `山田` になり、`山田　太郎` のようなセル内部の空白は保たれる。
3. 空行とトリム後に空になる行が削除され、ヘッダー行は削除されない。
4. トリム後に全列が一致する2行のうち、1行目だけが残る。
5. 列数が不正な行を含む CSV でも処理が完了し、その行番号が警告として表示される。
6. 10MB を超えるファイルと、デコードできないファイルは、それぞれ分かりやすいエラーで拒否される。

## 7. 仮定と未決事項

### 7.1 仮定（回答で直接決めていないため、暫定的に置いた内容）

- プレビューの行数は 50 行とする。
- ダウンロードするファイル名には `_tidy` を付ける。
- 各処理（トリム・空行の削除・重複の削除）の初期状態はすべてオンとする。
- クォートされたセルの中の改行は変更せずに保持する（改行コードの選択はレコードの区切りにのみ適用する）。
- 出力時のクォートは必要なセルにだけ付ける（Python の `csv.QUOTE_MINIMAL` 相当）。
- 実行環境は Python 3.12 以上とする。

### 7.2 未決事項（v0.2 以降で決める）

- 列の操作の具体的な UI と操作単位
- 値の正規化の対象（日付フォーマットの種類、数値の判定ルールなど）
- 変更サマリレポートや処理設定の保存を追加するかどうか

## 付録 A. 意思決定の記録

要件は質問と回答の形式で決めた。選択肢と採用理由を記録する。

| # | 質問 | 採用 | 主な理由・トレードオフ |
| --- | --- | --- | --- |
| 1 | 提供形態 | Web アプリ | ブラウザで操作できる。UI の実装と配布の負荷は増える |
| 2 | 利用者 | 学習・ポートフォリオ目的 | 機能は小さく保ち、品質とドキュメントを重視する |
| 3 | 整形機能 | 4分類すべて | 範囲が広いため、#8 で段階リリースにした |
| 4 | 言語 | Python | 標準の `csv` モジュールが堅牢で、文字コードも扱いやすく、pytest でテストしやすい |
| 5 | 構成 | FastAPI＋軽量フロント | 層を分けることでテストと設計の説明がしやすい。Streamlit、Flask、Pyodide は採用しなかった |
| 6 | 実行環境 | ローカルのみ | 運用の負荷がない。公開すると悪用対策と費用が課題になる |
| 7 | 操作フロー | プレビュー付き | 変更前後を確認できる。サマリレポートと設定の保存は範囲外にした |
| 8 | 進め方 | MVP から段階追加 | 各段階で動くものを記録でき、手戻りの影響を小さくできる |
| 9 | 入力文字コード | 自動判定＋手動上書き | 対象を UTF-8 と CP932 に絞ることで誤判定を減らし、誤判定したときも利用者が直せる |
| 10 | 出力形式 | 文字コードと改行を選択式 | Excel 向けの BOM 付き UTF-8 と CP932 に対応するため |
| 11 | 重複の定義 | 全列一致・先頭を残す | v0.1 では単純さを優先した。キー列の指定は列の操作 UI が必要なので後回しにした |
| 12 | サイズ上限 | 10MB | メモリ上でまとめて処理でき、実装が単純になる |
| 13 | 空白トリム | 前後の半角・全角空白 | 日本語データでよく必要になる。セル内部の空白を縮めると意図しない変更になりうるため対象外とした |
| 14 | 区切り文字・ヘッダー | カンマ固定・1行目をヘッダー | テストケースと UI を最小限にするため |
| 15 | 不正な行 | 警告を表示してそのまま出力 | データを勝手に捨てないため |
| 16 | 成果物の置き場所 | `docs/` | 開発の過程を記録するという README の趣旨に合うため |
