## 1. 目的と範囲

v0.1 の要件（FR・NFR）と受け入れ基準を、どのテストで、いつ確かめるかを決める。

- 対象: コア（整形処理）、API、画面、性能、ドキュメント
- 対象外: v0.2 以降の機能、Safari など対応外のブラウザ（要件定義書 3.2）

## 2. テストの種類

| 記号 | 種類 | 何を確かめるか | 道具 | 置き場所 | 実行する場面 |
| --- | --- | --- | --- | --- | --- |
| U | ユニットテスト | コアの関数を単独で動かし、入力に対する結果・変更記録・課題が正しいか | pytest | `tests/core/` | 毎回の CI、手元 |
| P | プロパティベーステスト | ランダムな入力を大量に作り、「常に成り立つ性質」が崩れないか（6章） | Hypothesis | `tests/core/test_properties.py` | 毎回の CI、手元 |
| I | 結合テスト | API にファイルと設定を送り、JSON・CSV・エラー応答が設計書 11 章のとおりか | pytest、FastAPI の TestClient | `tests/api/` | 毎回の CI、手元 |
| D | 依存の向きのテスト | コアが FastAPI・pydantic・api を import していないか（設計書 7.3） | pytest | `tests/test_dependencies.py` | 毎回の CI、手元 |
| E | E2E テスト | 本物のブラウザで画面を操作し、主要な流れが最後まで動くか | Playwright（pytest-playwright）、Chromium | `tests/e2e/` | 毎回の CI（別のジョブ）、手元 |
| PERF | 性能測定 | 10MB の CSV で 5 秒以内か（NFR-01） | pytest（`perf` マーカー）、Playwright | `tests/perf/` | 手元だけ。リリース前に実行して結果を記録する |
| M | 手動確認 | 見た目、Excel での表示、複数のブラウザ、README の手順など、自動化しにくいもの | 確認項目の一覧（7章） | この文書 | リリース前 |

### 2.1 方針

- **テストは機能と同じプルリクエストに入れる。** 開発計画の作業5〜9 では、その作業で作る要件のテストを一緒に書く。
- **不具合を直すときは、先にその不具合を再現するテストを書く**（回帰テスト＝一度直した不具合が再び起きないことを確かめるテスト）。
- **E2E は主要な流れだけにする。** 細かい見た目は手動で確かめる（開発者の決定）。
- **テストデータは、ほとんどをテストのコードの中で作る。** 代表的な CSV だけをファイルで置く（5章。開発者の決定）。

## 3. CI での実行

開発計画の作業4（`chore/setup-uv`）で、#3 の最小のワークフローを次の形に広げる。E2E のジョブは、画面ができる作業9（`feat/web-ui`）で追加する。

| ジョブ | 内容 | 失敗とする条件 |
| --- | --- | --- |
| `test` | `uv run pytest`（U・P・I・D）とカバレッジの測定。Python 3.11（最低の版）と 3.13 の2つで実行する | テストが1つでも失敗する。コアのカバレッジが 90% 未満（4章） |
| `e2e` | アプリを起動し、Chromium で E テストを実行する。Python 3.13 だけで実行する。失敗したテストは、操作の記録（トレース）を CI のアーティファクトとして 7 日間保存する | テストが1つでも失敗する |

E2E テストは作業9で `tests/e2e/test_web_ui.py` に作った。手元では次の手順で実行する。Playwright は E2E 用の依存グループ `e2e` に分けているので、`uv sync` だけでは入らない（`test` ジョブを軽く保つため）。Playwright が入っていない環境では、`tests/e2e/` のテストは集めない。

```sh
uv sync --group e2e
uv run playwright install chromium   # 初回だけ。Chromium をダウンロードする
uv run pytest -m e2e
```

別の版の Chromium しか使えない環境では、環境変数 `E2E_CHROMIUM_PATH` に Chromium の実行ファイルを指定する。

性能測定（PERF）は CI では実行しない。GitHub が用意する仮想マシンは性能が一定ではなく、5 秒という基準を安定して判定できないため。

## 4. カバレッジ

カバレッジ（テストで実行されたコードの割合）を pytest-cov で測る（開発者の決定）。

| 対象 | 測り方 | 基準 |
| --- | --- | --- |
| コア（`src/csv_tidy/core/`） | 行と分岐（`if` の両側）の両方 | **90% 以上。下回ると CI を失敗にする** |
| API（`src/csv_tidy/api/`） | 行と分岐 | 基準なし。CI の結果に表示する |
| 画面（JavaScript） | 測らない | E2E と手動確認で補う |

カバレッジは「テストで実行されたか」を示すだけで、「正しく確かめたか」は示さない。数値を上げるためだけのテストは書かない。

## 5. テストデータ

### 5.1 テストのコードの中で作るもの

`tests/helpers.py` に、CSV のバイト列を組み立てる関数を用意する。テストを読むだけで、何を入力しているかが分かるようにする。

```python
# 例: CP932・CRLF のバイト列を作る
data = make_csv(
    [["名前", "年齢"], ["  山田　", "30"]],
    encoding="cp932",
    newline="\r\n",
)
```

| 引数 | 内容 |
| --- | --- |
| 行の一覧 | 1 行を値のリストで書く。`None` を書いた位置は「セルなし」（行が短い）にする |
| `encoding` | `utf-8`、`utf-8-sig`（BOM 付き）、`cp932` |
| `newline` | `\n`、`\r\n` |
| `raw` | 書き方の誤りを試すときは、行の一覧の代わりに文字列をそのまま渡す（例: `'h1,h2\n"a,b\n'`） |

### 5.2 ファイルで置くもの（`tests/fixtures/`）

E2E と手動確認で、実際にファイルを選ぶ操作に使う。

| ファイル | 内容 | 使う場面 |
| --- | --- | --- |
| `customers_cp932.csv` | 画面の見本と同じ「顧客一覧」（1,000 行）。CP932・CRLF。前後の空白、空行、列数の不一致、重複を 1 つずつと、812〜813 行目にまたがるセルを含む。ゼロ幅スペース（U+200B）は CP932 で表せないため入れていない | E2E の主要な流れ、手動確認、README のスクリーンショット |
| `customers_utf8_bom.csv` | 上と同じ内容に、6 行目のゼロ幅スペースを加えて UTF-8（BOM 付き）で保存したもの | 手動確認（見えない文字の表示）、README のスクリーンショット |
| `broken_quote.csv` | 3 行目でクォートを閉じ忘れたもの | E2E（エラー表示） |
| `xss.csv` | `<script>alert(1)</script>` と `<img src=x onerror=alert(1)>` を値に含むもの | E2E（NFR-07） |
| `emoji.csv` | 絵文字と `—`（U+2014）を含むもの。CP932 で出力できない | E2E（ダウンロードできない状態） |
| `not_csv.xlsx` | 小さな Excel ファイル | E2E・手動確認（xlsx の案内） |
| `manual_check.csv` | 差分の色・記号・帯がひととおり出るように、前後の空白（半角・全角・タブ・NBSP）、除去しない文字（U+0085・U+2028）、空白を取ると数式になる値、ゼロ幅スペースだけが違う 2 行、DEL、空行、列数の不足、複数行のセル、重複を 1 行ずつ並べたもの。1 列目にその行で確かめることを書いてある。UTF-8（BOM 付き）・CRLF | 手動確認 M4、E2E（受け入れ基準 13・14）。作業10 で追加 |

これらのファイルは `tests/fixtures/make_fixtures.py` で作る（`uv run python tests/fixtures/make_fixtures.py`）。中身を変えるときは、このスクリプトを直して作り直す。1000 行中 999 行目だけを変える受け入れ基準 9 のデータなどは、E2E テストのコードの中で作る。

10MB の性能測定用のデータはリポジトリに置かず、`scripts/gen_bench_data.py` で毎回作る（設計書 5 章）。

## 6. プロパティベーステスト

プロパティベーステスト（ランダムな入力を大量に作り、常に成り立つ性質を確かめるテスト）を、次の性質に使う（開発者の決定）。どれも、例を数個書くだけでは見落としやすい境界を突くためのもの。

| # | 性質 | 何を防ぐか |
| --- | --- | --- |
| P1 | どんな値の表でも、CSV に書き出して読み直すと元の表に戻る。値にはカンマ、`"`、改行、空文字、全角文字を含める | 書き出しと解析のクォートの扱いの食い違い |
| P2 | トリムを2回かけても、1回かけたときと結果が変わらない（べき等＝何回行っても結果が同じ性質） | 取り除き方の漏れ |
| P3 | トリムの後の値は、先頭と末尾に対象の空白（半角・全角スペース、タブ、NBSP）がなく、それ以外の文字は1文字も変わっていない | 対象外の文字（U+0085 など）を消してしまう、内部の空白を消してしまう |
| P4 | 重複の削除の後は、列数と値が同じ行が2つ以上残らない。残った行の順番は元の順番のまま | 削除しすぎ、順番の入れ替わり |
| P5 | `records` に `changes` を当てはめて作った表と、`export` で出力した CSV を読み直した表が一致する | 差分表示と出力の食い違い（設計書 D2） |
| P6 | 上限以下のどんなバイト列を渡しても、コアは整形結果を返すか、決めた例外（`TidyError` の仲間）を出すかのどちらかで、それ以外の例外で止まらない | 想定外の入力での異常終了 |

### 11.2 仮定（テスト計画の段階で置いた内容。レビューで変更してよい）

- E2E は Python 版の Playwright（pytest-playwright）で書き、テストの言語を Python にそろえる。ブラウザは Chromium だけを使う。
- CI は Python 3.11 と 3.13 で実行する。
- 性能測定は CI で実行せず、リリース前に手元で行う。
- 画面の JavaScript には、単独のユニットテストを書かない。変更記録から表を組み立てる処理の正しさは、P5 と E2E で確かめる。
