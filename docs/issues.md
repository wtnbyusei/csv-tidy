## 詳細

### H1: 列数が合わない行の扱いが矛盾している（対応済み）

- 指摘: FR-31 の「内容を変えずに出力」と FR-20（トリムは各セルに適用）が矛盾していた。空行の判定や重複の判定を、列数が合わない行にどう適用するかも決まっていなかった。
- 検討: 末尾の空セルを無視して比較する案を出したが、`a,b,,`（4列で空）と `a,b`（2列でセルなし）を同じに扱ってしまい、元から2列の行だと誤解させるため採用しなかった。
- 決定: 列数も含めてそのまま比較する。トリムは列数が合わない行にも適用し、列数は変えない。画面ではセルがないことと空であることを見分けられるようにする。

### H2: CSV として解析できない場合の動作が決まっていない（対応済み）

- 指摘: Python の `csv` モジュールは、既定ではクォートの閉じ忘れを検出せず、ファイルの残りを1つのセルにまとめてしまう。131,072 文字を超えるセルはエラーになる。
- 決定: `strict=True` で解析し、閉じ忘れと閉じたクォート直後の不正な文字はエラーとして中止する。セルの長さの上限は引き上げる。余分なクォートがたまたま対になっている場合は検出できないため、複数行にまたがるセルを情報として表示して補う。

### H3: 変更前後の比較の定義があいまい（対応済み）

- 指摘: 先頭50行のプレビューでは、後方の行の変更が見えない。
- 決定: 処理中に記録した変更をもとに、変更前と変更後を左右に並べて表示する。既定は「変更箇所のみ」の表示とし、変更の件数も表示する。

### M1: CSV ではないファイルを受け入れてしまう（対応済み）

- 指摘: xlsx（ZIP 形式）は UTF-8 として、PNG は CP932 として読めてしまうことを確認した。
- 決定: NUL 文字を含むファイルは処理を中止し、xlsx の場合は CSV として保存し直すよう案内する。その他の制御文字は警告にとどめる。

### M2: CP932 に変換できない文字の表示件数に上限がない（対応済み）

- 決定: 出力を中止し、件数と最初の20件を表示する。差分表示でも該当するセルを強調する。

### M3: アップロードしたデータの保持場所が決まっていない（対応済み）

- 決定: サーバーは状態を持たない。ファイルはブラウザ側で保持し、設定を変えるたびに送り直す。

### M4: 画面表示の安全性と CSV インジェクション（対応済み）

- 決定済み: 画面に表示するセルの値は必ず HTML エスケープする（NFR-07）。
- 現状の要件: CSV インジェクション対策は範囲外（値を変更せず、警告も出さない）。
- 追加で見つかった論点: このツールの処理が、数式ではなかった値を数式に変えてしまう場合がある。
  - トリムで `␣=1+1` が `=1+1` になる。
  - v0.3 で全角の `＝` を半角にすると `=` になる。
- 検討した案「CSV 上で数値か文字列かを判定する」: 採用できない。
  - CSV には型の情報がない（RFC 4180）。セルを囲むクォートは区切りのための記法で、値の一部ではない。
  - Python の `csv` モジュールで確認した結果（2026-09-25）:

    | CSV の記述 | 読み込んだ値 |
    | --- | --- |
    | `=1+1` | `=1+1` |
    | `"=1+1"` | `=1+1`（クォートなしと同じ） |
    | `"""=1+1"""` | `"=1+1"`（値にクォート文字が含まれる） |
    | `"007"` | `007` |

  - Excel のセルに `"=1+1"` と入力すると文字列になるのは、先頭の文字が `=` ではなく `"` だからである。CSV では、値にクォート文字を含めるには `"""=1+1"""` と書く必要がある。
  - Excel で CSV を直接開くと、クォートで囲んでいても型が推測される（`"007"` が `7` になる現象と同じ）。このため `"=1+1"` も数式として扱われると考えられる。ただし、この開発環境では Excel での動作を確認できていない。
- 決定（2026-09-25）: 次の対応案を採用し、要件定義書に反映した（FR-48, NFR-09, 受け入れ基準13）。
  - 整形処理によって先頭が `=` `+` `-` `@` になったセルだけを警告し、差分表示で強調して件数を表示する。値は変更しない。
  - README の「制限事項」に、CSV インジェクション対策は行わないことを書く。
- 残作業: Excel で実際の動作を確認できれば、結果をここに追記する。
- 見直し（2026-10-06）: 「CSV インジェクション対策は行わない」は S1 で見直し、数式の無害化（FR-49）を追加した。

### Q1: 警告対象の制御文字の範囲（対応済み）

- 当初の要件: FR-18 の警告対象は U+0001〜U+001F（タブ・CR・LF を除く）だった。
- 論点: DEL（U+007F）と C1 制御文字（U+0080〜U+009F）を対象に含めるかどうか。
- 調査結果（2026-09-25、Python で確認）:
  - C1 制御文字は、UTF-8 のデータを Latin-1 として読んで保存し直した二重エンコードの文字化けで現れる（例: `’` が `â\x80\x99` になる）。CP932 のファイルにあるバイト 0x80 も U+0080 として読み込まれる。
  - DEL は通常のデータにはまず出てこないため、警告しても誤検知はほとんどない。
  - 制御文字ではない見えない文字（ゼロ幅スペース U+200B、ファイル途中の BOM U+FEFF）が混ざると、見た目が同じ行が重複と判定されない。
  - NBSP（U+00A0）は FR-20 のトリム対象に入っていなかった。
  - 実装上の注意: Python の `str.strip()` は NBSP のほかに U+0085 や U+2028 も除去し、FR-20 の範囲より広い。トリムは除去する文字を明示して実装する（例: `s.strip(" \t\u00a0\u3000")`）。
- 決定: 制御文字すべて（U+0001〜U+001F（タブ・CR・LF を除く）、U+007F、U+0080〜U+009F）と見えない文字（U+200B〜U+200D、U+2060、ファイル途中の U+FEFF）を警告し、差分表示では記号で見える形にする（FR-18）。NBSP をトリム対象に加える（FR-20）。受け入れ基準 14・15 を追加した。

### L1: 受け入れ基準1が自動テストで確認できない（対応済み）

- 指摘: 「Excel で開いても文字化けしない」は人が目で確かめる手順で、自動テストにできない。
- 決定: 自動テストでは「出力の先頭 3 バイトが `EF BB BF`（BOM）で、改行がすべて CRLF」を確認する。Excel で開いて確かめることは、手動の確認項目として分けた。

### L2: 受け入れ基準が足りない（対応済み）

- 決定: 受け入れ基準 16（手動上書き）と 17（処理ごとのオン・オフ）を追加した。

### L3: 性能目標が測定できない（対応済み）

- 指摘: 「数秒以内」では測れない。
- 決定: 「10MB（約10万行×10列）の CSV で、アップロードから差分表示までが 5 秒以内（開発に使う PC で測定）」とした。測定用のデータは生成スクリプトで作り、リポジトリに置く。

### L4: 境界値の動作が決まっていない（対応済み）

- 指摘: 10MB の定義と、空のファイル・ヘッダーだけのファイル・1行目が空行のファイルの動作が決まっていなかった。
- 決定:
  - 10MB は 10×1024×1024 = 10,485,760 バイト。ちょうどは受け付け、超えたらエラー（FR-02）。
  - 先頭の空行は飛ばし、最初の空でない行をヘッダー行にする。飛ばした行数は情報として表示する（FR-04）。
  - 0 バイトのファイルと空行だけのファイルはエラー。ヘッダー行だけのファイルは処理し、ヘッダー行だけを出力する（FR-08）。

### L5: 主な利用者の想定（対応済み）

### Q2: 公開方法（ConoHa WING での公開）（対応済み）

- 背景（2026-09-28）: 開発者は ConoHa WING（レンタルサーバー＝1台のサーバーを多くの利用者で共有するサービス）で WordPress を運用している。そこにこのツールを置いて、ポートフォリオとして誰でも試せるようにできないかを検討した。
- 調査結果（個人ブログの情報による。ConoHa 公式の文書では確認できていない）:
  - SSH で接続でき、Python は複数の版（3.11 を含むという報告あり）が用意されている。
  - Python の Web アプリは CGI（リクエストのたびにプログラムを起動して終了する方式）で動かす例が紹介されている。
  - サーバーを起動したままにする常駐プロセスが許可されているかは確認できなかった。共有サーバーでは一般に許可されない。
- 今の設計（FastAPI＋uvicorn の常駐）を WING で動かす場合の問題:
  1. 常駐できない可能性が高い。
  2. FastAPI は ASGI という方式で、CGI では変換用のライブラリが必要になる。リクエストのたびに読み込み直すため遅く、NFR-01（10MB で 5 秒以内）を満たせるか分からない。
  3. 10MB の処理で CPU とメモリを使い、共有サーバーの使用量の上限によって同じアカウントの WordPress が遅くなるおそれがある。
  4. 公開すると、他人のデータの扱い（プライバシー）、大量送信への対策、NFR-02（127.0.0.1 のみで待ち受け）の見直しが必要になる。
- 推奨案: v0.1 はローカル実行で完成させる。その後、公開用に Pyodide（ブラウザの中で Python を動かす仕組み）版を追加する。
  - WING にはファイルを置くだけで動き、サーバーに負荷がかからない。
  - CSV が利用者の PC から外に出ないため、公開してもプライバシーの問題が起きない。
  - コアは標準ライブラリだけで書く（NFR-03）ため、コアを変えずに再利用できる。取り替えるのは API の部分だけ。
  - 欠点: 初回に Pyodide 本体（数 MB〜十数 MB）の読み込みが必要。処理速度は通常の Python より遅いため、NFR-01 を満たせるか測る必要がある。
- 決定（2026-09-29）: v0.3 の完了後に、公開版として Pyodide 版（v0.4）を作る。機能がそろってから公開し、作り直しの手間を一度で済ませるため。要件定義書のリリース計画に v0.4 を追加した。
- 見直し（2026-10-01）: レンタルサーバー（ConoHa WING）には置かない方針に変更した。リポジトリを公開にしたため、Pyodide 版を作る場合は GitHub Pages（GitHub の無料のサイト公開機能）で公開できる。Pyodide 版は「公開候補」とし、作るかどうかは v0.3 の完了後に決める。ConoHa 公式文書での確認は不要になった。
- 設計への影響: v0.4 でコアをそのまま Pyodide で動かせるよう、v0.1〜v0.3 のコアは標準ライブラリだけを使い、ファイル・ネットワーク・スレッドなどブラウザで使えない機能に頼らない（設計書 1章）。

### S1: CSV インジェクションへの対策（M4 の見直し、対応済み）

- 経緯（2026-10-06）: M4 では、元の値を書き換えないことを優先し、CSV インジェクション（`=` などで始まる値が表計算ソフトで数式として実行される問題）への対策（値の無害化）を範囲外にしていた。v0.1 の完成前に、開発者が「セキュリティが不安」として対応することを決めた。
- 確かめた資料: OWASP（Web のセキュリティの指針をまとめている団体）の「CSV Injection」。危険な先頭の文字は `=` `+` `-` `@`、タブ、CR、LF。日本語の環境では全角の `＝` `＋` `－` `＠` も数式として扱われることがある。対策は、先頭に `'` を付ける方法と、先頭にタブを付ける方法（Excel で確かめられた方法）が挙げられている。どちらも、Excel で保存して開き直すと効かなくなることがあると注意されている。
- 決定（2026-10-06、開発者）:

  | 論点 | 決定 | 理由 |
  | --- | --- | --- |
  | 方法 | 先頭に `'` を付ける | OWASP の基本の対策で、付けたことが目に見える。タブは目に見えず、このツールで読み直すとトリムで消える |
  | 数値として読める値（`-5`、`+81` など） | 対象外 | 数式にならない。対象にすると数値が文字列になり、計算できなくなる |
  | 全角の `＝` `＋` `－` `＠` | 対象にする。数式化の警告（FR-48）も全角に広げる | OWASP が日本語の環境での注意として挙げている |
  | 初期状態 | オン | 何もしなくても安全な出力になるようにする。変更の原則（1.1 節）に、安全のための処理の例外として書き加えた |

- 反映先: 要件定義書 第10版（1.1、FR-24、FR-46、FR-48、FR-49、NFR-09、受け入れ基準 13・24、付録 A の 37）。M4 の決定のうち「値の無害化は範囲外」はこの決定で置き換えた。

### Q3: v0.3 の全角→半角変換で意図しない書き換えが起きる（検討中）

- 論点（2026-09-28）: 全角→半角の変換は値を書き換える。「データを勝手に変えない」方針と矛盾しないか。
- 整理: 方針の意味は「利用者が選んでいない変更や、気づけない変更をしない」こと。トリムと同じく、利用者が選び、差分表示で確認でき、元のファイルが残るなら方針に沿う。
- 問題: 一般的な NFKC 正規化（Unicode の規格で定められた、見た目が同じ仲間の文字を1つの形にそろえる変換）をそのまま使うと、全角英数字以外も変わる。Python で確認した結果:

  | 変換前 | 変換後 | 問題 |
  | --- | --- | --- |
  | `ＡＢＣ１２３` | `ABC123` | 意図どおり |
  | `ｶﾞｷﾞ` | `ガギ` | 半角カナが全角になる（方向が逆） |
  | `㈱山田` | `(株)山田` | 1文字が4文字になる |
  | `①②` | `12` | 「1と2」が「12」という1つの数になる |
  | `Ⅲ` | `III` | 1文字が3文字になる |
  | `㍻` | `平成` | 記号が文字列になる |
  | `ｍ²` | `m2` | 「平方メートル」の意味が消える |
  | `＝ＳＵＭ（Ａ１）` | `=SUM(A1)` | Excel の数式になる |

- 「データを変えない」との矛盾について（2026-10-01）: このツールの目的はデータを整えることなので、変えること自体は目的に含まれる。誤解を避けるため、要件定義書 1.1 に「変更の原則」（利用者が選んだ処理だけ変える、変更はすべて見せる、元のファイルは書き換えない）を明文化した。全角→半角の変換もこの原則に沿えば矛盾しない。
- 正規化の目的: 表記が違うだけで別の値として扱われることを防ぐ。例: `ＡＢＣ` と `ABC` が検索や重複判定で一致しない、全角の数字が計算に使えない、`2026/9/1` と `2026-09-01` が同じ日付として並べ替えられない。
- 正規化の危険: 意味まで変える変換。例: `01/02/2026` は1月2日とも2月1日とも読める。郵便番号や商品コードの `001234` を数値にすると先頭の `00` が消える。v0.3 では「表記だけを変えて意味は変えない」変換に限る。
- 方針案（v0.3 の要件定義で決める）:
  1. 初期状態はオフにし、利用者が選んだときだけ変換する。
  2. NFKC をまるごと使わず、全角英数字（`Ａ`〜`Ｚ`、`ａ`〜`ｚ`、`０`〜`９`）と、決めた記号だけを対象にする。`①` `㈱` `²` などは変換しない。
  3. v0.2 の列の操作を土台に、列ごとに対象を選べるようにする。
  4. 差分表示と、数式化の警告（FR-48）で変化を知らせる。
