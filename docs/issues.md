## 詳細

### H1: 列数が合わない行の扱いが矛盾している（対応済み）

- 指摘: FR-31 の「内容を変えずに出力」と FR-20（トリムは各セルに適用）が矛盾していた。空行の判定や重複の判定を、列数が合わない行にどう適用するかも決まっていなかった。
- 検討: 末尾の空セルを無視して比較する案を出したが、`a,b,,`（4列で空）と `a,b`（2列でセルなし）を同じに扱ってしまい、元から2列の行だと誤解させるため採用しなかった。
- 決定: 列数も含めてそのまま比較する。トリムは列数が合わない行にも適用し、列数は変えない。画面ではセルがないことと空であることを見分けられるようにする。

### H2: CSV として解析できない場合の動作が決まっていない（対応済み）

- 指摘: Python の `csv` モジュールは、既定ではクォートの閉じ忘れを検出せず、ファイルの残りを1つのセルにまとめてしまう。131,072 文字を超えるセルはエラーになる。
- 決定: `strict=True` で解析し、閉じ忘れと閉じたクォート直後の不正な文字はエラーとして中止する。セルの長さの上限は引き上げる。余分なクォートがたまたま対になっている場合は検出できないため、複数行にまたがるセルを情報として表示して補う。

### H3: 変更前後の比較の定義があいまい（対応済み）

- 指摘: 先頭50行のプレビューでは、後方の行の変更が見えない。
- 決定: 処理中に記録した変更をもとに、変更前と変更後を左右に並べて表示する。既定は「変更箇所のみ」の表示とし、変更の件数も表示する。

### M1: CSV ではないファイルを受け入れてしまう（対応済み）

- 指摘: xlsx（ZIP 形式）は UTF-8 として、PNG は CP932 として読めてしまうことを確認した。
- 決定: NUL 文字を含むファイルは処理を中止し、xlsx の場合は CSV として保存し直すよう案内する。その他の制御文字は警告にとどめる。

### M2: CP932 に変換できない文字の表示件数に上限がない（対応済み）

- 決定: 出力を中止し、件数と最初の20件を表示する。差分表示でも該当するセルを強調する。

### M3: アップロードしたデータの保持場所が決まっていない（対応済み）

- 決定: サーバーは状態を持たない。ファイルはブラウザ側で保持し、設定を変えるたびに送り直す。

### M4: 画面表示の安全性と CSV インジェクション（対応済み）

- 決定済み: 画面に表示するセルの値は必ず HTML エスケープする（NFR-07）。
- 現状の要件: CSV インジェクション対策は範囲外（値を変更せず、警告も出さない）。
- 追加で見つかった論点: このツールの処理が、数式ではなかった値を数式に変えてしまう場合がある。
  - トリムで `␣=1+1` が `=1+1` になる。
  - v0.3 で全角の `＝` を半角にすると `=` になる。
- 検討した案「CSV 上で数値か文字列かを判定する」: 採用できない。
  - CSV には型の情報がない（RFC 4180）。セルを囲むクォートは区切りのための記法で、値の一部ではない。
  - Python の `csv` モジュールで確認した結果（2026-09-25）:

    | CSV の記述 | 読み込んだ値 |
    | --- | --- |
    | `=1+1` | `=1+1` |
    | `"=1+1"` | `=1+1`（クォートなしと同じ） |
    | `"""=1+1"""` | `"=1+1"`（値にクォート文字が含まれる） |
    | `"007"` | `007` |

  - Excel のセルに `"=1+1"` と入力すると文字列になるのは、先頭の文字が `=` ではなく `"` だからである。CSV では、値にクォート文字を含めるには `"""=1+1"""` と書く必要がある。
  - Excel で CSV を直接開くと、クォートで囲んでいても型が推測される（`"007"` が `7` になる現象と同じ）。このため `"=1+1"` も数式として扱われると考えられる。ただし、この開発環境では Excel での動作を確認できていない。
- 決定（2026-09-25）: 次の対応案を採用し、要件定義書に反映した（FR-48, NFR-09, 受け入れ基準13）。
  - 整形処理によって先頭が `=` `+` `-` `@` になったセルだけを警告し、差分表示で強調して件数を表示する。値は変更しない。
  - README の「制限事項」に、CSV インジェクション対策は行わないことを書く。
- 残作業: Excel で実際の動作を確認できれば、結果をここに追記する。

### Q1: 警告対象の制御文字の範囲（対応済み）

- 当初の要件: FR-18 の警告対象は U+0001〜U+001F（タブ・CR・LF を除く）だった。
- 論点: DEL（U+007F）と C1 制御文字（U+0080〜U+009F）を対象に含めるかどうか。
- 調査結果（2026-09-25、Python で確認）:
  - C1 制御文字は、UTF-8 のデータを Latin-1 として読んで保存し直した二重エンコードの文字化けで現れる（例: `’` が `â\x80\x99` になる）。CP932 のファイルにあるバイト 0x80 も U+0080 として読み込まれる。
  - DEL は通常のデータにはまず出てこないため、警告しても誤検知はほとんどない。
  - 制御文字ではない見えない文字（ゼロ幅スペース U+200B、ファイル途中の BOM U+FEFF）が混ざると、見た目が同じ行が重複と判定されない。
  - NBSP（U+00A0）は FR-20 のトリム対象に入っていなかった。
  - 実装上の注意: Python の `str.strip()` は NBSP のほかに U+0085 や U+2028 も除去し、FR-20 の範囲より広い。トリムは除去する文字を明示して実装する（例: `s.strip(" \t\u00a0\u3000")`）。
- 決定: 制御文字すべて（U+0001〜U+001F（タブ・CR・LF を除く）、U+007F、U+0080〜U+009F）と見えない文字（U+200B〜U+200D、U+2060、ファイル途中の U+FEFF）を警告し、差分表示では記号で見える形にする（FR-18）。NBSP をトリム対象に加える（FR-20）。受け入れ基準 14・15 を追加した。

### L1: 受け入れ基準1が自動テストで確認できない（対応済み）

- 指摘: 「Excel で開いても文字化けしない」は人が目で確かめる手順で、自動テストにできない。
- 決定: 自動テストでは「出力の先頭 3 バイトが `EF BB BF`（BOM）で、改行がすべて CRLF」を確認する。Excel で開いて確かめることは、手動の確認項目として分けた。

### L2: 受け入れ基準が足りない（対応済み）

- 指摘: 文字コードの手動上書きと、処理のオン・オフに対応する受け入れ基準がなかった。
- 決定: 受け入れ基準 16（手動上書き）と 17（処理ごとのオン・オフ）を追加した。

### L3: 性能目標が測定できない（対応済み）

- 指摘: 「数秒以内」では測れない。
- 決定: 「10MB（約10万行×10列）の CSV で、アップロードから差分表示までが 5 秒以内（開発に使う PC で測定）」とした。測定用のデータは生成スクリプトで作り、リポジトリに置く。

### L4: 境界値の動作が決まっていない（対応済み）

- 指摘: 10MB の定義と、空のファイル・ヘッダーだけのファイル・1行目が空行のファイルの動作が決まっていなかった。
- 決定:
  - 10MB は 10×1024×1024 = 10,485,760 バイト。ちょうどは受け付け、超えたらエラー（FR-02）。
  - 先頭の空行は飛ばし、最初の空でない行をヘッダー行にする。飛ばした行数は情報として表示する（FR-04）。
  - 0 バイトのファイルと空行だけのファイルはエラー。ヘッダー行だけのファイルは処理し、ヘッダー行だけを出力する（FR-08）。

### L5: 主な利用者の想定（対応済み）

- 指摘: 回答は「学習・ポートフォリオ目的」だったが、要件定義書には「開発者本人」と解釈して書いていた。
- 決定（2026-09-27）: 使うのは開発者本人。加えて、ポートフォリオとして採用担当者などが GitHub で見たり動かしたりすることを想定する。README に概要、スクリーンショット、起動手順、主な設計判断を載せ（NFR-12）、起動は数個のコマンドで完了するようにする（NFR-05）。

### L6: 範囲外の項目が抜けている（対応済み）

- 決定: 対応ブラウザを最新版の Chrome・Edge・Firefox とし（NFR-10）、表示言語は日本語のみとした（NFR-11）。UTF-16 などの文字コード、多言語対応、それ以外のブラウザでの動作確認を範囲外に追加した（3.2）。

### L7: Python のバージョンの前提がずれている（対応済み）

- 決定: NFR-06 を「Python 3.11 以上」に変更した。開発環境が 3.11.15 で、3.12 固有の機能を使う予定がないため。

### L8: 文書の版とリリースの版がまぎらわしい（対応済み）

- 決定: 文書の版を「第N版」と表記し、リリースの版（v0.1 など）と区別した。
